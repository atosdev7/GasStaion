# Smart210 cashier app

Qt app for the Smart210 board: Qt 5.3.2, GCC 4.5.1 (FriendlyARM arm-none-linux-gnueabi). Write C++03 style: no `nullptr`, `auto`, range-for, `override` or `final`. The same code also builds with a newer desktop Qt, which is how screens are tried on a PC.

## Layout

| Folder | What |

Each screen's `.cpp`, `.h` and Qt Designer form `.ui` are together: `core/` (`AppConfig` (config.ini), `Fonts`, `Theme`, `Translations`, `Database`, `Migrator`, `Settings`, `Session`, `Barcode`, `PosHash`), `shell/` (`main.cpp`, `MainWindow`, `AppShell` with the header, footer and sidebar forms, `TabbedPage`), `login/` (first run: `SetupFlow`, `SetupPage`, `LoginPage`, `FirstSyncPage`), `sales/`, `supplies/`, `remainders/`, `cards/` (screens, `CardLedger`, `CardReader`), `dispensers/` (`DispensersPage`, `NozzleDialog`, `BoardProtocol`, `BoardBus`, `BoardClock`), `ticket_debt/`, `review/`, `settings/` (`SettingsPage`, `MachineConfigPage`, `ServerForm`, `PinPage`), `sync/` (`ApiClient`/`ApiReply` (HTTP), `SyncClient`, `SyncStore`, `Uploader`, `Purger`), `printing/` (`PrintService`, `EscPos`, `TicketRenderer`) and `input/` (scanners, Hangul input) |

## Build

Open `smart210.pro` in Qt Creator with the Smart210 kit (Qt 5.3.2) for the board, or with a desktop kit for a PC.

## Settings (`config.ini` next to the program)

```ini
language=en
fullscreen=true
width=1280
height=720
fontDir=/path/to/fonts
dataDir=/path/to/sdcard/smart210
```

All keys are optional: language `en`, fullscreen on, 1280 x 720 when not fullscreen, fonts folder and data folder (the database `smart210.db`) next to the program. On the board point `dataDir` at the SD card. Use `fullscreen=false` on a PC. English is the only language (Chinese was removed 2026-10-22). The machine configuration is not kept in the database but in an INI file apart from the SD card (`deviceFile` in `config.ini`; default `smart210/device.ini` in the user's config folder, which is the board's own flash): the server address and port, the device name, the printer address and port, the converter port and the tank of each nozzle. A replaced SD card then needs no new setup: the first-run page already shows the server address, and the printer, converter and nozzle tanks are back when the tanks are downloaded and the boards answer. A terminal made before this still has the values in its database; they are read from there until they are saved once. Everything else (sales, tickets, the cashier's session, sync state, ...) is kept in the database (task 4.2).

## Korean font

The board has no Korean font, which the Hangul input needs. Copy any `.ttf`, `.otf` or `.ttc` that covers Korean into the `fonts` folder next to the program (an open font such as Noto Sans CJK KR; do not ship a Windows font). The first family that supports Korean becomes the application font, Latin text included. The Settings page shows the family in use.

## Database

SQLite, in `smart210.db` inside `dataDir`. `Database::open` sets WAL with full synchronous writes (a committed sale survives a power cut), a 5 second busy timeout and foreign keys. Use one connection per thread, each with its own name.

`Migrator` runs the numbered scripts `resources/migrations/NNN_name.sql`: script N moves `PRAGMA user_version` from N-1 to N, each in its own transaction, so a failing one changes nothing. A database newer than the program is refused. Never edit a migration that has shipped: add the next number (and list it in `resources.qrc`). A script may also hold lines `-- add-column-if-missing: <table> <column> <definition>`: `Migrator` adds that column only where the table lacks it (SQLite has no ADD COLUMN IF NOT EXISTS), for a column that an old database misses and a new one was made with: `006_card_holder_phone.sql` (2026-10-25: a terminal database made before `cards.holder_phone` was put into `001_initial.sql` could not register a card).

Write the SQL for SQLite 3.8.4, the version inside Qt 5.3.2: no UPSERT, `RETURNING`, `RENAME COLUMN`, `DROP COLUMN` or window functions (use `INSERT OR REPLACE`, rebuild a table to change it). A test scans the scripts for these, because a desktop Qt has a newer SQLite and would not complain.

Conventions (also at the top of `001_initial.sql`): kg, money and litres are INTEGERS x100 and density x10000, so sums are exact; a ticket barcode is its 16-digit number as an INTEGER (`Barcode::toKey` / `fromKey` add the leading zeros back); records made here carry a `synced` flag (0 until uploaded) and a pull must not overwrite a row that is still unsynced. `Settings` is the key/value table for the server address, token and so on.

On the board the Qt build needs the SQLite driver plugin (`sqldrivers/libqsqlite.so`), or Qt built with it linked in.

## First run and the web API

The web app knows this terminal by its **IP address**: the admin adds it on the web app's Devices screen. There is no token and no sign-in. Until the device has saved a server (settings `server_host` and `device_id`), the window opens on the **Server Setting** page: address and port and a **Test Connection** button (`GET /api/ping`). If the server answers that this terminal's address is registered, the address, port, device id and name are saved and the home page opens; if not, the page shows the address the admin has to add. The first sync (4.3) will follow, starting with `POST /api/sync/begin` when the database is empty, and the cashier login (4.4) uses the users that sync downloads.

The program talks plain HTTP to the web app on the station's network (`ApiClient`, `ApiReply`): every call has a 10 second timeout, tells apart "no answer", "not JSON", a refusal with the server's message and a `busy` server (503, backup running), and sends nothing to identify itself: the server uses the caller's address. The logic is in `SetupFlow` (no widgets, tested against a fake server); `SetupPage` is only the screen. Server messages are shown as sent (English).

## Sync

`SyncClient` downloads and `Uploader` uploads (both over `ApiClient`). They are separate on purpose: the download runs by itself **every minute**, the upload when the cashier presses Upload data or, in the modes "At close of day" and "Continuous" of Machine Config (Server tab, setting `upload_mode`), by itself (`AutoUpload`, see Upload below).

- **Download:** the first time it calls `sync/begin`, then config (replaced whole) and every table page by page: each page is stored in one transaction and then acknowledged, and the last step of the first run is `initial-done` (the first-sync gate: `initial_done` setting). A pulled ticket or loan that was changed here and not uploaded yet (`synced = 0`) is kept and not acknowledged, so the web app sends it again after the upload. A busy or unreachable server ends the run and keeps what was stored.
- **Pace and the server's limit:** the calls of the whole program leave one second apart (`ApiClient`, 60 a minute) and the web app lets an address make 200 a minute (`API_THROTTLE_PER_MINUTE`), so a call is normally never refused. If the server still answers **429** (too many requests), the call is not failed: `ApiReply` waits as long as the `Retry-After` header says (5 seconds when there is none, at most a minute), tells `ApiClient`, which holds back every call of the program for that long, and sends the same request again, up to 5 times and 2 minutes in all (a limiter refuses a call before anything is done with it, so asking again is safe). After that the reply ends as **busy** ("The server is busy (too many requests), try again in a minute."), as for a backup, and the next beat tries again.
- **Upload:** tables go in the API's order, 200 rows a batch. Saved rows get `synced = 1`; refused rows stay with the server's reason in `upload_errors`, and are not sent again in the same run. A sale deleted here before the upload, the loan made with it and any ticket that is not sold or supplied are never sent.
- **Numbers:** `Decimal` converts between the API's strings ("12.50") and the stored integers.
- **In the window:** `MainWindow` shows the Server Setting page until the server knows this terminal, then the first-sync gate (a Downloading page with Retry on failure) until `initial_done`, then Sales (there is no home page). Once set up it downloads by itself at start and every minute (fixed; the terminal sees the web app's changes within a minute), uploads by itself only in the automatic upload modes, and runs `Purger` after each successful download. A download also asks the web app which of the uploaded sales and supplements the accountant has **confirmed** (`POST /api/confirmed`) and removes those (`Purger::removeConfirmed`: with their items, their printed remainders and their finished tickets; a sold ticket that is not supplied yet stays; a card's top-ups and old supplies are never removed but **hidden** once confirmed, `hidden = 1` (migration 011): the Review screen and the checkout do not list them, the card's balance and history are untouched; a server that does not know the question is left alone).
- **Purge:** `Purger` removes what is older than the device's purge days (set on the web Devices screen) and safe to lose: uploaded sales, supplements, remainders and settlements; sales deleted here before an upload with their ticket and loan; finished tickets. Never anything not uploaded (a refused record included), ticket loans, or tickets still in stock or sold.
- **A clock that is behind (2026-11-01):** a new sale, card top-up, card ticket, loan settlement, scanned ticket or manual supply is refused while the clock is more than 2 minutes behind the newest record this terminal stamped (a sale or top-up, a remainder, a started fill; `Clock::behindRecords`: a power cut with a flat RTC battery); the message gives the time of that record. A download that sets the clock makes it work again.
- **Time zone and clock** (`Clock`; the manual of the Smart210 kit, `用户手册.pdf`, 7.3.23: the board has a real-time clock chip with a backup battery, its date from the factory is not right, `date -s` sets the system clock and `hwclock -w` writes it to the RTC): the web app tells in every answer to ping, device and config its time in the station's zone (`APP_TIMEZONE`), the same moment in UTC, the name of the zone and its offset from UTC now. Every download (a minute) does three things with them. (1) The **time zone** of the program is the station's: the offset is kept (`utc_offset_seconds`, `timezone_name`) and applied as a fixed POSIX `TZ` (`UTC-9` for UTC+9, no zone files needed on the board), at once and again at the next start, and it follows daylight saving time because the offset comes with each download; the 9 AM business day and every time on the screens are the station's. (2) How far the clock is from the server's is measured **in UTC**, so it does not depend on the zone, and the footer warns above 60 seconds. (3) With `setSystemClock=true` (the default for a Linux program that runs as **root**, as on the board; off on a PC) a clock more than 5 seconds off is set with `date -u -s` and written to the RTC chip with `hwclock -w -u` (also tried with `-f /dev/rtc0`), so the time survives a power-off; the nozzle boards get the new time at once. The manual says the supplied image already runs `hwclock -s` at boot (rcS), which puts the RTC time back into the system clock. The Settings page shows the zone (`UTC+09:00 (Asia/Seoul)`). An older server that sends only its local time is compared as before.

## Login

The web app knows the terminal by its address, so who is using it is a separate thing: the **cashier**. After the first download the app shows the **Login** page: the cashiers (users with the cashier role that the web app marked for the terminal, active, not deleted: managers, assistants, accountants and administrators do not sign in on the terminal) by name, and a password. The password is checked on the device against the salted hash that came with the users (`PosHash`: SHA-256, or the older SHA-1 by length), so it works offline. The login stays: later starts open straight into the app until Log out, which is on the **Settings** page (the Settings button on the home page), never on the main screen. At every start the session is checked: a cashier the web app disabled or deleted is asked to log in again. `Session::userId()` is what records carry as `user_id`. A cashier added on the web appears on the login page after the next download.

## Spot sale

The Sales screen has a **Spot sale** tab (`SpotSalePage`), arranged like the spot sale form of the web app: the customer, the fuel type (priced from the download) and the price per kg (it can be changed for this one sale); the weight, the amount and the payment method (always cash, shown read-only); what the fuel is for (sale, self use, other, ticket loan; self use and other use take the customer **Individual**, the one the download marks with `is_default`, and cannot be changed; a sale starts with Individual too, the buyer who pays cash and needs no name, and what is known about them goes in the comment; a ticket loan needs a customer to be chosen); the **Result** (below); then the **Receipt issued** box and the comment. The cashier types the weight or the amount: the other follows from the price and the one typed last counts, so an amount of 100.00 stays 100.00 even when the weight is rounded. Only a sale has an amount; the sale is always cash and paid in full (debts are made on the web). `SpotSale::create` writes the sale, its ticket and, for a ticket loan, the loan in one transaction, all waiting for the upload (`synced = 0`, `sale_date` is the business day of the moment, filled in at once; the moment of the sale is its `created_at`, with `updated_at` for its last change). The ticket is minted on the spot: sign + the code (the first digit is the fuel type, 1 gasoline or 2 diesel; the second the kind of the ticket: 1 spot sale, 2 self use, 3 other use, 4 ticket loan, 5 card, 9 remainder; so 21 is a diesel spot sale) + a serial above `ticket_serial_base`, counted per code; `TicketNumbers` never repeats a number, even after a purge or on a replaced board (the config download brings the sign, the reserved codes and the highest serial the web app already holds). A sale without those numbers (nothing downloaded yet) is refused.

**Keyboard only** (`EnterChain`, 2026-10-25, for the cashier who does not want the mouse): on the spot sale and on the ticket sale **Enter moves to the next field** and Enter or Space on the **Save sale** button saves. The order is the order of the form (spot sale: customer, fuel type, price, use, weight, amount, result, receipt, comment, Save sale); a field that is switched off (the amount of an own-use sale, the customer of own use) is jumped over; in a combo box Enter moves on, and it only picks an entry while the list is open; Space ticks the receipt box. The cursor starts at the **weight** on the spot sale and at the **customer** on the ticket sale, and goes back there after every saved sale (a refused sale keeps it on the button). On the ticket sale Enter in the count adds the item and the cursor goes back to the spec for the next item; **one more Enter there, with nothing typed, means no more items** and goes on to the receipt (an arrow key or typing in the spec makes it a plain Enter again); Enter in the start serial goes to the count. The question of a spot sale set directly (the nozzle dialog) is answered with the keys too: the first free nozzle is chosen when it opens and the list has the cursor, the arrow keys choose another (a busy nozzle is jumped over), Enter is OK and Escape is Cancel. The focus shows as a blue border on fields, buttons and the receipt box (`theme.qss`), and the buttons of the sidebar no longer take the Tab key. `EnterChain` is an event filter that is given the widgets of a form in order (`add`, `manual` for one that keeps its own Enter, `jumpFrom` for the one-time jump); the chain works on the Qt 5.3 code base (C++03). Tests: `theSpotSaleIsFilledWithTheKeyboardAlone`, `theTicketSaleIsFilledWithTheKeyboardAlone`, `otherUseIsIndividualTooAndALoanNeedsACustomerWhoIsChosen`. The tests of the whole suite need the native Windows platform (the offscreen platform crashes in `QMessageBox`).

**Result** (2026-10-29): a **Result** box on the spot sale screen and on the Fill page of a card says what the sale or the fill gives, *Print ticket* or *Set directly*. The cashier's **Settings** page has two choices, **Spot sale** and **Card fill**, each *Print ticket* (the default) or *Set directly*: they are only the **default value** of the two boxes, which take it whenever their page is opened; the box can be changed for a sale and stays as it is until the page is opened again, and it does not change the setting (`SettingKey::SpotSaleResult`, `CardFillResult`, in the device file, `Settings::resultIsDirect`). *Print ticket* prints the sale's ticket as soon as the sale is saved. *Set directly* prints nothing: after the sale is saved a question (`NozzleDialog`) lists the nozzles of the sale's fuel type that work in auto mode, with what each one is doing; the cashier chooses a free one and presses **OK**. The nozzle is chosen on its board, then the sale's ticket goes to the nozzle's queue and the fill starts with the weight as the preset, exactly as when the supplier scans the ticket (`SupplySession::add` and `start`), so the result is recorded the same way and the ticket is used. Cancel, a nozzle that does not answer in 5 seconds or a refusal of the board leave the sale and its ticket saved and say so; **Print again** then prints the ticket. The same code (`DirectSet`) serves a **card fill**: with *Set directly* the ticket the card pays for (`Cards::issueTicket`) is not printed, the nozzle question opens, and with no nozzle chosen the ticket stays for Print again or Cancel ticket.

**A card fill is always made with a ticket** (2026-11-01, user: "use only ticket-based fill for card again"): the card pays for the ticket when it is made and the unused part comes back to the card. The fill without a ticket (kg held on the card, `card_holds`, `CardSupplyDialog`, migration 013) that a cloud session added was removed. **The balance on the dispenser:** when the cashier reads a card, the dispenser shows its balance (SHOW_BALANCE, `SupplySession::showCardBalance`, only while the nozzle is idle and answers): the nozzle chosen on the Settings page (**Card balance shown on**: Automatic, Off or Nozzle n; `SettingKey::CardBalanceNozzle`) or, Automatic, the first auto nozzle of the card's fuel type that is free.

**Three rules that follow the web app** (2026-10-31, from the audit of the terminal against the web): (1) a **free payment card** (the manager sets it on the web; the cards download carries `free_payment`, migration 012) may be topped up at a price of 0, any other card needs a price above 0; (2) the Review screen moves a record only to a day that is not after today and not more days back than the web app allows a cashier (`sale_backdate_days` of the config, 3: `ReviewData::dateProblem`); (3) the business day starts at the hour the web app says (`business_day_start_hour` of the config, 9: `Checkout::startHour`, kept in the settings and applied at the start and after each download).

## Ticket sale

The Sales screen has a **Ticket sale** tab (`TicketSalePage`), arranged like the ticket sale form of the web app. Top: the **customer**, the **fuel type** (the fuel types that have tickets in stock) and the **price per kg** (filled from the download, changeable for this sale). Then the **Tickets to sell** panel: at the left the *add item* area, with the **spec** (with how many tickets are in stock), the **start serial** (filled in with the first serial in stock after the items already in the table, or empty for "the lowest ones"), the **count** and the **end serial** (read only, it follows from the start and the count), a **Check** button that says *Valid: serials 11 to 12 can be sold.* or *Not valid: some tickets from 11 to 12 are not available to sell.*, and **Add item** (it adds only when the check is valid); at the right the table of the items with spec, count, the start and the end as full barcodes (the first and the last ticket of the item) and the weight, and a **Clear list** button (a double click on an item asks and takes that one item out). Under it: the total (tickets, kg and, for a sale, the amount), the **Receipt issued** box, the use (sale, self use, other, ticket loan; as in the spot sale, always cash and paid in full) and the comment, then **Save sale**. The serials of the items are worked out in the order of the items like the web form (`TicketSale::take`, `TicketSale::resolve`): a start serial asks for that run, every ticket of it in stock; a ticket is given once; a change of the fuel type starts the items again. There is no scanning on this screen. `TicketSale::create` takes the tickets of the items and keeps the items as entered in `sale_items` (spec, count, first and last serial, weight; the upload sends them inside the sale's row, `items`), checks every ticket again inside the transaction (a download may have changed one), writes the sale (with the receipt, `1` or empty), turns the tickets to sold and, for a loan, adds the loan, all with `synced = 0`; if any ticket is no longer sellable nothing is written. The terminal has no cost and no sale date on this screen: the web app fills the cost, and the sale gets its date (the business day of the moment) when it is saved.

## Review and upload

**Review** (sidebar) is where the cashier checks the day and uploads. Pick the **date**; the **Sales**, **Supplies** and **Ticket Debt** tabs list that day's records with their totals (sales: spot, ticket, total paid, unpaid). A record without a date yet shows under the business day of its time (the business day runs from 9 AM to 9 AM); a record made within 30 minutes of 9:00 has its date cell marked, because it may belong to either day. Select a record (one at a time) and change its **comment** (Save comment) or its **date** (date picker, Set date): such a record is marked not uploaded again and goes up with the next **Upload data**, which sends only the records that wait on the date chosen at the top (and the tickets that belong to them); the button counts only those, while Home and the footer count all dates. The State column says Waiting, Uploaded or Refused (the reason is in the tooltip). The nozzles are not records: they are not counted and go up first with any upload. A record the accountant has confirmed on the web cannot be changed any more: the web app refuses the change and the record shows as Refused.

The changes made on Machine Config (a nozzle's config, the converter port, the printer or the server address) are written to a text file on the SD card, `changes.log` in the data folder, one line each: `2026-10-09 10:54:57: nozzle:1: old -> new (Cash One)`. They are not kept in the database and never uploaded.

## Look and layout

The look of the program is made of two kinds of files, both edited in **Qt Creator** (no C++ needed):

- **`src/<folder>/<Class>.ui`**: the layout of each screen, made in **Qt Designer** (open the file in Qt Creator). `src/cards/CardPage.ui` is the form of the screen `CardPage`, and so on: `AppShell`, `SideBar`, `ShellHeader`, `ShellFooter` (the frame), `HomePage`, `LoginPage`, `PinPage`, `SettingsPage`, `SetupPage`, `ServerForm`, `FirstSyncPage`, `SpotSalePage`, `TicketSalePage`, `NozzleDialog`, `LoanSettlePage`, `LoanSettleDialog`, `SupplyPage`, `ManualSupplyPage`, `RemainderTicketsPage`, `CardHistoryDialog`, `DispensersPage`, `ReviewPage`, `MachineConfigPage`, `CardPage`, `TabbedPage`. The C++ class of a screen keeps the logic: it makes its form with `setupUi` and finds the widgets by their names, so **do not rename a widget** (its object name) without changing the code and the tests, but move, resize, add and re-arrange them freely (layouts, margins, spacing, minimum sizes, stretch). The texts in a form are translated like the ones in code: run `lupdate` afterwards (see Translations). Things that are filled in at run time stay in the code: the columns of the tables, the items of the combo boxes, the validators, the supply table's colours (`colorOf`), the sidebar's key to button mapping.
- **`resources/theme.qss`**: colours, fonts and spacing of every kind of widget (one style sheet, with comments). **To try a new look without a build**, copy it next to the program, put `themeFile=/path/to/theme.qss` in `config.ini` and start the app: the file is read again every time it is saved. A message gets its colour from the property `state` (`error`, `warning`, `ok`, `muted`; the code says `Theme::setState(label, "error")`), a sub title from `heading`, bold text from `bold`, the cards of the home page from `card`, the buttons that must not be pressed by mistake from `state="danger"`.

Font sizes are in pixels and follow three rules, set in `theme.qss`: **20 px** for everything by default, **24 px** for menu items, sub titles and buttons, **28 px** for page titles (a label named `pageTitle`) and the company name. `Theme::BodyPx` (20) is also the size the Chinese font is loaded at.

**Hangul input** (`HangulInput`, `HangulComposer`, `HangulKeyMap.h`; from the chat "Qt5 Asian language input on smart210"): a keyboard (USB or PS/2) can type Korean in any text field. It is an event filter on the application, with no screen of its own. The program starts in **English** (the keys pass through untouched: barcodes, numbers, Latin text); the **Hangul key** or **Ctrl+Space** switches Hangul on and off, and the footer shows `A` or `한`. In Hangul mode the letter keys give jamo (Dubeolsik, the table is `HangulKeyMap.h`; Shift gives the double consonants and ㅒ ㅖ) that the composer builds into syllables; the syllable being composed is the preedit of the field; Space, Enter, digits and the arrows commit it, Backspace takes the last jamo off it, Ctrl/Alt shortcuts commit it and go on. Fields that hide what is typed (the PIN fields) are never touched. `hangul=false` in config.ini turns the whole thing off. The board needs a font with Hangul glyphs in the `fonts` folder (Noto Sans CJK covers Korean; WenQuanYi Micro Hei has no Hangul). Written for C++03 (Qt 5.3); tested on Qt 5.15 (`theHangulComposerBuildsSyllables`, `theHangulInputTypes...`).

Every screen after the login sits in the shell (`AppShell`): a **header** (company logo and name at the left, the cashier and the date and time at the right), a **sidebar** (Sales, Supplies, Cards, Dispensers, Ticket Debt, Review, Settings, each with an icon), a **footer** (the status: last download, clock warning, dispensers online, supplier scanner, the Hangul input mode, records waiting for upload) and the **content**. Sales has the Spot sale and Ticket sale tabs, Review has the day's records and the Upload data button. To change the **logo and the company name**, replace `resources/brand/logo.png` and edit `resources/brand/company.txt` (the first line is the name, UTF-8), then rebuild: they are Qt resources. The sidebar icons are `resources/icons/*.png` (white outlines, 48 x 48, for the dark sidebar).

## Supply screen

The **Sessions** tab of Supplies (`SupplyPage`) only *shows* what the supply does in the background; nothing on it controls the supply. The six nozzles are listed with their fuel type, mode, the status of the session, the tickets (total kg - count) and the weight dispensed so far (updated about four times a second). Clicking a nozzle shows its queued tickets in the table below the list (barcode, fuel type, amount); it does not choose the nozzle at the dispenser. Without a click the table shows the nozzle the supplier chose last. `SupplySelection` holds the logic of the choice (current nozzle, SELECT / DESELECT, the poll flags). **The select key only tells, the app chooses**: a nozzle board has the states IDLE, SET (preset loaded), DISPENSING and DONE and **no selected state**. The board reports the key in its next POLL answer (SELECT_KEY); the app makes that nozzle the current one in its own state (one nozzle at a time, the one chosen last; the Sessions tab shows it as *Selected*) and sends it the SELECT command: the board beeps and nothing else changes. The key of the current nozzle pressed again lets it go (nothing is sent). A nozzle that loses the choice before its fill started (queued tickets, nobody took the gun up) gives its preset back: SET_PRESET with zero, the board is IDLE again; its tickets stay in the queue and the preset is set again when it is chosen again. The scanned tickets go to the current nozzle, and the preset is set on it. The clear key is reported too (CLEAR_KEY): the app drops the queue and sends SET_PRESET with zero (the cancel) to a board that has a preset.

**Tickets sold on paper before go-live (2026-10-27).** The config download brings the ranges of the press publishes dated before the web app's go-live date (`ticket_legacy`, stored in the table `ticket_legacy`, migration 010; `TicketLegacy`). A scan (the Sessions tab, the typed entry, the loan settlement) of a ticket with **no row** that is inside a range makes its row at once: sold, the weight of its spec, the day of the publish as the day it was sold, counted as uploaded; a ticket that has a row follows its row (one still in the stock room is *never sold*); one outside the ranges is *not known*. The use is reported like any other (the ticket as supplied), and the web app makes the same row from that report. The purger never deletes the rows of these tickets, or a used one would be accepted a second time. Two terminals that accept the same old ticket offline are told apart on the web app (the second report is a logged conflict).

**Enter ticket (2026-10-26).** A ticket whose barcode cannot be scanned (smudged, torn) is typed in the **Enter ticket** box of the Sessions tab, above the tickets table: the **11 digits after the station sign** (the code and the serial) or all 16 digits, spaces and dashes ignored; **Enter** or **Add**. `SupplySession::typed` completes the 11 digits with the station sign (`ticket_sign`, from the config download; without it the 16 digits are needed) and adds the ticket to the queue of the nozzle whose tickets the table shows (the row that was tapped, else the one chosen with the select key; a tapped nozzle that is not the chosen one is chosen first, its board beeps) through the same checks as a scan (sold, the nozzle's fuel type, in no other queue, auto mode). When it was added the box is cleared; when it was refused the message says why and the digits stay to be corrected. The tickets that this terminal prints show the 16 digits under the bars (`GS H 2`), so the number can be read from the ticket.

### Supply session (auto and manual mode)

**Supplies** has two tabs. **Sessions**: the status of each nozzle's session is **Queued** (tickets were scanned, the preset is not on the board yet), **Set** (the preset is on the board and the dispenser shows it), **Working** (the gun is up and the fill runs) and **Done** (the fill ended and was recorded; its tickets stay in the table for 10 seconds and then go); a nozzle without a session shows the live state of its board (free, selected, no answer, ...). A fill paid with a card is one row with the customer's name and the preset.

**How the supply works in the background** (protocol v0.4): the supplier chooses the nozzle with its **select key at the dispenser** and scans the tickets with the supplier's scanner (a ticket must be sold, of the nozzle's fuel type and in no other queue; a refused scan says why on the screen). Every ticket that joins the queue makes the program send the queue's total as the **preset** (SET_PRESET) and the dispenser shows it. The supplier takes the **gun up** (the hook of the dispenser): the board only reports it (GUN_UP in the poll). The program then checks: with tickets queued and their preset on the board it saves the session, locks the queue and **sends START**; if the queue was cleared it sends no START and sets the preset to zero. The **clear key** of the dispenser drops the preset (the board raises CLEAR_KEY) and the program drops the queue; once the fill runs, the clear key does nothing. When the fill ends the app reads the result, saves the supplement and its tickets, and only then lets the board forget the result. If less came out than the tickets cover, the rest is a **remainder ticket** (printed; **Print the ticket** on the Remainders screen if the printer did not take it). A fill that stops at its preset within 0.05 kg leaves no remainder (the station keeps it). A fill paid with a card is a ticket like the others (the Cards screen makes it, see *Cards*): the supplier scans it at an auto or a manual nozzle.

**Remainders** is a part of the program of its own (sidebar), not a tab: the remainder tickets of the supplies, to print again. Its sidebar button turns amber while a ticket is not printed (the tip says how many).

**Manual input** (the second tab) is for the **manual-mode nozzles**. **A manual board is out of the polling** (2026-10-25: `BoardBus::setBoardPolled`, set by `NozzleConfigSync::syncBoards` from the nozzle's mode in the database): it gets no POLL, is neither online nor offline (the pages say "Not polled") and shows no status, and the app never reads, acknowledges, records or remembers anything about its fills; only a command that is asked for (Update or Read of its config) is sent to it and answered, and the board is polled again once its nozzle is changed to auto. The cashier types the supply in here. **Only a nozzle in manual mode can be chosen** there; its **density** is shown. The cashier types the **tickets** that paid for the supply, one barcode at a time with the keyboard (Enter or Add ticket); each must be sold, of the nozzle's fuel type and in no queue. Their total is the **preset**; the **dispensed kg** is set to it by itself and the **remainder** is 0 (dispensed + remainder = the tickets). The cashier types either the dispensed kg or the remainder, the other follows; the **litres** follow from the kg and the density (litres = kg / density; the litres field is read only: it is never typed). The date and time default to now, and cannot be earlier than the start of the day that many days back as **Machine Config, Options, Manual supply** says (the admin sets the days, default 3, 0 = today only; `manual_supply_days`, kept in the device file); a time in the future is refused too (`SupplySession::recordManual`, the editor stops at the earliest day). The tickets must cover the dispensed kg (more than they cover is never accepted). What is left of them is a **remainder ticket** (a new ticket, saved with a remainders row and printed, as with an automatic fill), unless it is 0.05 kg or less: the tolerance only ever favours the station. **Save supply** (`SupplySession::recordManual`) writes the supplement (mode `manual`) with its tickets for the upload at once. It is refused while a fill runs on the nozzle or a result waits. The old tabs *Tickets to assign* and *Reading by hand* are gone. `SupplyQueue` (queue and session), `SupplyRecord` (supplement, remainder), `SupplySession` (scanner, preset, gun start, result, board commands), `SupplyPage` (Sessions), `ManualSupplyPage`, `RemainderTicketsPage`. The **Comment (optional)** field under the tickets is kept as the comment of the supplement (it goes up with it). The **Remainders** screen has a **Comment** column and a field with **Save comment** for the chosen remainder: the comment is saved with the remainder, which is marked not uploaded, so it goes up with the next upload (migration `003`, `SupplyRecord::setRemainderComment`).

## Supplier scanner

The supplier's barcode scanner is a USB HID keyboard. It is read in the background (`SupplierScanner`, a thread running a `ScannerReader`) straight from its Linux input device and grabbed with `EVIOCGRAB`, so what it scans never types into a screen; the cashier's scanner is an ordinary keyboard into the focused field and is not involved. The board has no udev and `eventN` changes from one start to the next, so the device is found each time in `/proc/bus/input/devices` by its **exact name** (`supplierScannerName` in config.ini, default `SCANNER SCANNER`) and, to tell two scanners of one name apart, optionally a part of its USB port (`supplierScannerPhys`, for example `usb-s5p-ehci-1.1`). To see the name and port, plug the scanner in and run `cat /proc/bus/input/devices` on the board. If the scanner is missing or unplugged the reader looks again every second. Signals: `barcodeScanned(QString)` and `connectedChanged(bool)`. On a PC (no evdev) it does nothing; `boards = false` in config.ini turns it off.

## Nozzle boards

**The nozzles are added by hand** (2026-10-24; before, every board that answered made a nozzle by itself). On **Machine Config > Dispensers** the technician picks a free address (1 to 6, `MachineConfig::NozzleCount`; the nozzle number is the board's address), the fuel type and, if wanted, the tank, and presses **Add nozzle** (`MachineConfig::addNozzle`): only the nozzles that were added are asked on the RS485 bus (`BoardBus::setBoardEnabled`, `NozzleConfigSync::syncBoards`), shown (Dispensers, Supplies, the nozzle list of a fill, the footer count) and used. A board that answers at another address is ignored and makes no nozzle. The **Remove** button in the row of a nozzle (it asks "Remove nozzle N?" and removes only after Yes) takes it away: it is switched off on the bus and the web app is told (the nozzle goes up with `deleted`; a removed nozzle and a new one with the same number go in the order they were made); it is refused while a fill is open on it, and its records stay. **The nozzles go to the web app by themselves**, whatever the upload mode is (`Uploader::uploadNozzles`): right after a nozzle is added, removed or changed on Machine Config, and at every beat of the automatic upload (each minute) for what waits (a change reported by a board, a failed try). Only a nozzle that has a tank goes (the web app needs it); the records still wait for the cashier or the upload mode. **The config of a nozzle (mode, fuel type, density, pulses per litre) is kept in this terminal's database, and nothing is fetched from a board by itself** (2026-10-24; before, every board that came online was read and what it reported replaced the stored config). A nozzle that was just added holds its fuel type, its tank and the density of that fuel from the web app, and no pulses yet: its config counts (`Nozzle::seen()`; the pages say "Config not set" until then) once it was saved (Update) or read from the board (Read). On **Machine Config > Dispensers** the form of the picked nozzle has two buttons (`NozzleConfigSync`): **Update** checks what is typed, **saves it in this terminal's database first** (`MachineConfig::saveConfig`, logged) and then tries to send it to the board (SET_CONFIG), comparing the board's answer (the config it stored) with what was sent: when they are the same the page says "Verified"; when the board does not answer, is busy or does not keep it, the page says the config is saved here but the board was not updated, and Update can be pressed again. **Read** asks the board of the picked nozzle for its config (GET_CONFIG) and saves what it reports (a board that holds no config yet is not saved: "The board holds no config yet. Send one."). **Machine Config > Dispensers** shows the nozzles that were added with their status and the config this terminal holds. **Rules (2026-10-25):** a nozzle must be connected to a tank that holds its fuel type (Add nozzle is refused with a box when there is none, `MachineConfig::addNozzle`; Update is refused when its fuel type would leave it with none; Read is not saved in that case); **Update and Remove are refused with a box while a fill is open on the nozzle or tickets are queued on it** (`MachineConfig::configBlocker`, `removeBlocker`: the queued tickets were checked against the nozzle's fuel type, and a removed number would keep them); a nozzle whose saved config the board has not confirmed (an Update that could not be sent or that the board did not keep) is marked **Board differs** (the setting `nozzles_not_on_board`, kept across restarts) until a verified Update or a Read. The tank is the web app's, not the board's: it is chosen when the nozzle is added, shown in the table at once, and the config form has no tank field (it follows the fuel type when that changes). The tank is picked on the page (taken automatically when only one tank holds the fuel type), kept here and uploaded with the next upload, before the supplements; a supplement names its nozzle by number. The config download does not send nozzles. The same tab sets the port the converter connects to (default 4001). `boards = false` in config.ini turns the listening off (trying screens on a PC). **The name of a nozzle** (2026-10-26, `nozzles.name`, migration `007_nozzle_name.sql`): up to 50 characters, typed in the **Name** field of *Add a nozzle* or, for a nozzle that is added, in the **Name** group of its form (the field and **Save name**: only the name, the board is not asked; logged in the change log as `name - -> name Diesel 1`); the **Name** column of the nozzle table comes right after the number. The form of the picked nozzle has two groups, **Name** (the field and Save name) above **Config** (mode, fuel type, density, pulses per litre, Update, Read), and the fields of the Config use the width of the group. It goes up with the nozzle (`name`, null when it has none) and the web app shows it in its lists. The lists of this terminal show the name where they showed the number (the Supplies and Dispensers tables, the nozzle lists of the cards and of Manual input, the Review and Remainders tables, the nozzle dialog); a nozzle without a name shows as before ("Nozzle 3" or its number).

`BoardBus` talks protocol v0.3 (see `PROTOCOL.md`) to the nozzle boards behind one RS485-to-Ethernet converter. The Smart210 is the TCP server: the converter is set to TCP client mode and connects to the Smart210's port by itself (a new connection replaces the old one). It is a polling master: boards are asked in turn, one request at a time, and the answer to POLL carries the board's state and key flags. There are no quick retries; a missing or spoiled answer is dropped and the next round asks again (same SEQ, so the board repeats its last answer and never runs a command twice). Three missed rounds in a row make a board offline; it is then tried every 2 s. Use it as: `setListenPort(port)`, `addBoard(address)`, `start()` (false and `errorText()` when the port is taken), then `select`, `setPreset`, `startFill`, `getResult`, `ackResult` and the others, and listen to `polled`, `commandDone`, `commandFailed`, `boardOnlineChanged`, `connectionChanged`. Only tested against a fake board so far (`tests/FakeBoards.h`).

## Printing

The ticket of a **spot sale** is printed when the sale is saved, and the cashier can print it once more: the **Print again** button on the spot sale screen. The ticket is 80 x 50 mm and has, top to bottom: the long title of the ticket type, the fuel name with the weight and the date and time, the barcode, and the company logo. Text and logo are bitmaps (the printer has no Korean font, and the title may use a font of its own); the barcode is a bitmap too since 2026-10-29 (Code 128 subset C of the 16 digits with the digits under the bars, `TicketRenderer::barcodeImage`: a virtual ESC/POS printer printed nothing for the printer's own barcode command, a bitmap is printed by every printer). `printBarcode=printer` in `config.ini` brings back the printer's own command (`EscPos::barcode128C`). `TicketRenderer` builds the bytes, `PrinterConnection` sends them over TCP (port 9100), asking the printer for its status first: an out-of-paper, offline or cover-open printer gets no job and the cashier is told; a printer that does not answer the question is sent the job anyway. The sale is saved before printing, so a failed print never loses it.

**Title and footer as bitmaps, the fuel as a letter (2026-11-01):** the title and the footer of the ticket can be ready black-and-white bitmaps of 192 x 48 dots (`PrintOptions::titleBitmapPath`, `titleBitmaps`, `footerBitmapPath`; `TicketRenderer::bitmapStrip`): `title.bmp` and `footer.bmp` next to the program are used when they exist, or the files of `ticketTitleBitmap` and `ticketFooterBitmap` in `config.ini`; a title of one kind of ticket has its own key `ticketTitleBitmap_<kind>` (`sale`, `self`, `other`, `ticket_loan`, `remainder`, `card`). They are printed at their own size (never scaled), centred on a strip as wide as the paper, with a grey picture turned into dots at the middle grey. The title bitmap replaces the title text and the footer (under the barcode) replaces the logo; a missing file means the text and the logo as before. The details line prints the **letter** of the fuel, `A` (gasoline) or `D` (diesel), not its name.

Set the printer's address on **Machine Config > Printer** (with a **Check printer** button that only asks for its status). Options in `config.ini`: `printWidthDots` (576 for 80 mm paper, 640 on some printers), `logo` (a picture file, default `logo.png` next to the program; no file, no logo), `ticketFont` (a font file for the ticket text), `printEnd` (`cut`, `label` for a printer with a label sensor, or `none`) and the long title of each use `ticketTitle_sale`, `ticketTitle_self`, `ticketTitle_other`, `ticketTitle_ticket_loan`, `ticketTitle_remainder` (defaults are translated).

## Checkout

The date of a record is the **business day** it belongs to: a business day runs from 9 AM to 9 AM, so a sale at 02:00 belongs to the day before. The web app confirms records by this date. **The date is filled in when the record is made** (`sale_date`, `supply_date`, `remainder_date` and the `date` of ticket loans and settlements: `Checkout::businessDay` of the moment of the record), so every record has it from the start; the cashier can still change it on Review (Set date). `Checkout` is now only the catch-up for records made by an older version of the program, which have no date yet: it stamps them with the business day of their own time at start (the days that are over) and before an upload (everything). Its helpers (`businessDay`, `dateExpression`, the report of a day, moving the records of a day to the previous or next day) are unchanged.

## Ticket loan settlement

The **Ticket Debt** screen (`LoanSettlePage`) lists the loans that still have a balance (customer, fuel, date, loaned, settled, balance). The cashier chooses one and presses **Settle**: a dialog (`LoanSettleDialog`) opens for that debt, and the tickets the customer brings back are scanned (or typed with their 16 digits) into its list, each checked at once. A ticket must be sold (not in stock, used or restricted) and of the loan's fuel (`LoanSettlement::scan`), the same rules as the web app: otherwise anyone could settle a loan with an unsold ticket and get free fuel. **Settle** in the dialog supplies each ticket (no supplement: it paid the loan), writes a settlement row with the ticket's own weight and raises the loan's settled total; more than was lent is accepted like on the web. **Close** leaves without doing anything. The settlements are uploaded as they are.

## Dispensers

The **Dispensers** screen is read only: for each nozzle the **mode**, **fuel type** and **density** its board reported, the **preset** (what is set on the board: the weight of the session that runs, or of the tickets that wait; a manual nozzle's amount is typed at the dispenser and not known), the weight **dispensed** so far and the **status**. The pulses per litre are not shown (they are on Machine Config).

## Deleting a mistaken sale

On the **Review** screen (Sales tab) a spot sale that was entered wrong is deleted: the cashier enters the correct sale and then selects the wrong one and presses **Delete sale**. The first press only asks (the button says *Confirm delete* for six seconds), the second deletes. `SaleDeletion` allows it only while nothing has moved on: a spot sale of the logged-in cashier that is not uploaded, whose ticket was not used (no fuel was dispensed) and is not waiting in a nozzle's queue (a sale set directly has its weight as the preset of the board: the ticket must be taken out of the queue first), and whose loan has nothing settled against it. Selecting a sale says at once why it cannot be deleted (another cashier's sale, a ticket sale, uploaded, used, settled). Deleting marks the sale (it is not listed any more), restricts its ticket (it stays linked to the sale, so the number is not reused) and deletes its loan; none of the three is ever uploaded, so the web app never learns of the sale. After the purge days the deleted sale is purged with its ticket and loan. Ticket sales and uploaded sales are not deleted on the terminal: the assistant or accountant does that on the web (delete or counter entry).

## Upload data

The footer says how many records wait for the upload. **Review** has the **Upload data** button: the check screen of the chosen date: totals of what waits, a tab for each kind of record (sales, supplies, remainders, ticket loans, settlements) and a **Refused** tab with the reasons the server gave for records it did not accept. The cashier checks them and presses **Upload data** (`Uploader`). The button is off when nothing waits, cannot be pressed twice, and after a failed upload (no connection, a busy server) the screen says so and nothing is lost. `UploadSummary` counts with the same conditions as the upload, so the screen shows exactly what would be sent. Records that were uploaded (`synced = 1`) are final on the terminal: the later screens may only delete or change records that were not uploaded yet.

**Upload modes** (Machine Config, Server tab, "Upload to the server"; kept with the other machine settings, `upload_mode`): **Manual** (the default: only the button), **At close of day** (every minute the records made before the start of the running business day, 9 AM, go up by themselves; today's stay so that they can still be fixed or deleted) and **Continuous** (the records older than `AutoUpload::GraceMinutes`, 30 minutes, go up; time to delete a mistaken sale). The automatic upload never waits for the button, never runs while a download or another upload runs, and does not send a record the server refused (it would be refused again every minute): **Upload data** tries those again. A failed upload loses nothing; it is tried again at the next beat. `Uploader::upload(date, before)` has the optional `before` moment for this.

**Sales without a receipt** (Machine Config, Options tab, "Review screen"; kept with the other machine settings, `show_sales_without_receipt`, default shown): a box that shows or hides, on the **Review** screen, the sales that have no receipt (the **Receipt issued** box of the sale forms was not ticked: the column `sales.receipt` is empty or 0). Only the list is shortened: the totals above it still count every sale, and a line under them says how many sales are not listed. A change is written to the change log ("Sales without a receipt: yes -> no"). Nothing is deleted or left out of the upload.

## Settings and Machine Config

**Machine Config is a page of its own** (2026-10-24): not a part of the cashier's program. It has the whole window, with no sidebar, header or footer, and is opened only from the **Settings** button of the login screen, after the PIN (nobody is logged in then). Its tabs, by what they are about: **Server** (the address and port, Test Connection, the upload mode), **Dispensers** (the converter port, then the nozzles and their config), **Printer**, **Card reader**, **Options** (what the cashier's screens show: the sales without a receipt on the Review screen) and **Maintenance** (the latest changes, and the two resets). **Clean Data** erases the whole database of the terminal (tickets, sales, supplies, cards, users, the session, the sync state) and keeps the machine settings: the terminal downloads everything again. It is refused, and its button is shut, while any record waits for the upload (they exist nowhere else). **Clear Config** erases the machine settings (the device file: server address, printer, converter port, the tank of each nozzle, card reader, upload mode, options, and the same keys an older terminal kept in the database) and keeps the data: the terminal asks for the server again. Each button needs a second press within six seconds; after it the change is written to the change log (`Reset`) and the program starts again (`MainWindow::restartRequested`, `AppReset`).

The Settings page after the login has **Log out** and the about text (the server and this terminal): **a cashier who has logged in cannot reach Machine Config**. It is opened from the **Settings** button at the bottom right of the **login screen** (nobody logged in; the sidebar is off until someone logs in; Cancel and Back return to the login). Machine Config asks for the device **PIN** (the one the admin sets on the web Devices screen; its salt and hash arrive with the config download and are checked on the device, so it works offline) every time, and only then opens the config page: the server address (the same form as the first-run page; a changed address is tested before it is saved), the **pulses per litre** of each nozzle (stored x100 in `nozzle_config`, apart from the nozzles table that every download replaces) the **card reader** (port, speed, framing) and the **latest changes**. Every change is written to `changes.log` (no cashier is logged in then, so the line has no name). If the web app has no PIN for the device, Machine Config stays closed.

## Cards

The **Cards** screen (sidebar) is for the RFID fuel cards. A card is only its id; what it holds is a balance in kg of one fuel type. Put a card on the reader: the program opens this screen by itself, wherever the cashier is (after the login), and shows the card. On the board the id is only read, never typed (the box is read only); on a PC, where there is no reader, the box can be typed in and Enter reads the id like a card put on the reader (2026-10-25, for testing) (there is no *Find card*). The **History** button of a known card opens a dialog with the latest 10 top-ups (time, kg, price, paid) and the latest 10 fills (time, kg, litres), newest first (`CardHistoryDialog`). Everything about the cards is on this one screen: the card's information and, for a registered card, **the Fill page, the main work of a card (2026-10-26)**: a card that was just read shows the Fill form with **the cursor in its first field**. A **Top Up** button sits **above History** in the card's box and shows the Top Up page (its text becomes *Fill*, which brings the Fill page back); the same card read again keeps the page, another card starts on the Fill page. The button is off while no registered card is shown. **Keyboard**: **Enter** in a field moves on to the next one (`EnterChain`), and Enter on the button at the end presses it. The order of the fields: Fill: weight, **PIN**, OK (the PIN is the last field); Top Up: weight, price per kg, total payment, button. **Top Up and OK first ask "OK / Cancel"** (`ConfirmDialog`, OK is the default so Enter confirms): the question says what will be done (the kg and the card holder, the price and total, or what the card holds); the checks that can fail (no weight, more than the card holds) are shown before it, and the PIN is looked at only after OK, so Cancel counts no wrong PIN and changes nothing.

**Card ledger.** The web app keeps a ledger of every card (`card_transactions`): an entry for each top-up and each fill with the running balance of the card after it, and a *reversal* entry when a top-up or fill is deleted on the web, so the history survives deleted sales and cleared records. The entries are made on the web from the sales and supplements the terminal uploads (and from top-ups made on the web), in the order of the moments they happened; the terminal only **pulls** them (table `card_transactions`, migration `002`, `SyncStore::storeCardTransaction`). The **History** button of the Cards screen (`CardHistoryDialog`, `CardLedger::entries`) lists the latest 50 entries newest first: time, top-up / fill / reversal, kg in or out, the balance after it, and for a top-up the price and what was paid. What this terminal has made and the web app has not entered yet (not uploaded, or not pulled back yet) is added on top and marked *not confirmed yet*, with a balance that goes on from the last entry. The balance of a card on the terminal is still `cards.balance_kg` (the web balance, which is the sum of the ledger, plus what is not uploaded yet).

- **Not registered** (a new card on the reader shows this form): the cashier types the customer's **name** (only a name, not a web customer) and **phone number** (optional), picks the fuel type and types the **PIN** the customer gives, twice. The PIN is kept as a salted SHA-256 (`pin_salt`, `pin_hash`), never as typed, and the card waits for the upload.
- **Top up**: kg at a price per kg (the fuel's price is filled in and can be changed) and the **total payment**; typing the kg gives the total (kg x price), typing the total gives the kg and the typed total is what is paid (a total of 100.00 stays 100.00); paid in cash, in full: a sale of type `card` (`sales.card_id`), no customer, no ticket. A locked card can be topped up, a blocked (lost) one cannot.
- **Fill** (2026-10-26; before it there were *Fill Auto* and *Fill Manual*, with a nozzle to choose): the cashier takes the card, types the **kg** to supply (not above the balance) and the **PIN** the customer says, and presses **OK**. After "OK / Cancel" the PIN is checked (a wrong PIN counts, the **5th wrong one locks** the card, only the web app unlocks it; a right one counts from zero again), and `Cards::issueTicket` does it all in one transaction: the **balance falls by the kg at once** and a **ticket** for them is made, like the ticket of a spot sale: the next number of the reserved code *direct* (21, `TicketNumbers`), the card's fuel type, status *sold*, **no sale**, `tickets.card_id` (migration `008_ticket_card.sql`), waiting for the upload. The ticket is **printed** (`PrintService::printCardTicket`, title *Gas Station Card Fuel Ticket*; no printer or a printer that fails only gives a message) and the **supplier scans it** at the dispenser, at an auto or a manual nozzle, like any ticket: no nozzle is chosen on this screen, and the fuel that does not come out comes back as a **remainder ticket** (the usual rule: no refund to the card). Next to the form (to its right: the screen is not high enough for one under the other) the **last ticket of the card that is not used yet** is shown (`Cards::lastTicket`) with **Print again** and **Cancel ticket**: a ticket that waits for its upload and is not in the queue of a nozzle is deleted and its kg go back to the card (`Cards::cancelTicket`, after "OK / Cancel"); one that was uploaded is cancelled by the manager or the accountant on the web app (restrict the ticket: the kg go back to the card there). A fill that was started with a card before this change keeps its `supplements.card_id` and is recorded the same way (`SupplyRecord`, by the saved session); no new one is started.
- **Print count (2026-10-26)**: every ticket has `tickets.print_count` and `last_printed_at` (migration `009_ticket_print_count.sql`). `PrintService` adds one (and sets the time, and `synced = 0` so the ticket goes up again) each time the printer **took** a ticket: a spot sale's ticket, a remainder ticket and a card ticket, the first print and every *Print again*; a print that fails counts nothing. The Last ticket box of the Cards screen shows *Printed: n*. The upload carries both fields; a download keeps the larger count.
- The balance, the uploads and the history count the tickets made for a card: `Cards::issueTicket` moves `cards.balance_kg` itself; the upload sends the ticket with its `card_id` (and no sale); a card download keeps the unuploaded tickets off the balance the web app sends (`SyncStore::storeCard`); the History dialog shows a ticket as a fill (*not confirmed yet*) until the web app's entry comes back (its `source_id` is the 16 digits of the ticket). The Checkout and the date filters of the upload date such a ticket by the business day of `sale_date`.

`cards.balance_kg` is the web app's figure at the last pull plus the top-ups and minus the tickets (and the older supplies) made here and not uploaded yet (a top-up or a fill changes it in the same transaction), so it is right at once. A pull of a card that waits for its upload here is skipped and not acknowledged (the web app sends it again after the upload). `Cards` holds the rules (register, PIN, top-up, tickets), `CardPage` the screen, `CardReader` the serial reader. The terminal never unlocks, blocks or changes the PIN of a card: the manager or the accountant does that on the web app.

**Card reader** (Machine Config > *Card reader*): the serial port (default `/dev/ttyUSB0`, 8N1), the speed (default 9600), how the id comes (ends with CR / LF, or a fixed number of characters), the **text before the id** (default `CARD:`) and what the bytes are (ASCII text, or hex digits). The station's own reader is an Arduino Uno that sends one line `CARD: <uid>` per card (and other lines such as `Ready` after it resets): a line that does not start with the text is ignored and the text is cut off the others; clear the field for a reader that sends the bare id. An original Uno appears as `/dev/ttyACM0`, a clone with a CH340 chip as `/dev/ttyUSB0`. A reader that repeats the line while the card lies on it is fine: the same card read again only refreshes the screen and keeps what the cashier typed. `CardFrameParser` cuts the bytes into ids (STX / ETX and spaces dropped, capital letters); a fixed frame that stops short is forgotten after 0.3 s. The port is opened with termios on Linux (this Qt build has no QSerialPort); on a PC there is no reader and the id is typed. The reader is started when the program starts and again when its settings are saved; an unplugged reader is tried again every 3 seconds.

The supplements and remainders follow the names of the web app (`001_initial.sql`): `out_amount_lt`, `out_amount_kg`, `preset_kg`, `density` (kg per litre x10000, from the nozzle's board config), `mode` (`auto` / `manual`; a reading typed by hand is `manual`), `supply_date`; remainders `created_at` and `remainder_date`.

## Translations

Every user-visible string is written in English inside `tr()` and translated in the `.ts` files. After adding or changing strings:

1. `i18n\update_ts.bat` (runs `lupdate` for each group of screens on the files listed in `i18n\<page>.lst` and adds the new strings of the code **and of the `.ui` forms** to the `.ts` file of that page; a new `.cpp` / `.ui` file that has `tr()` strings must first be added to the list of its page, and a new page needs its `.lst`, its lines in `update_ts.bat` and `resources.qrc`, and its name in `src/Translations.cpp`),
2. translate the new entries,
3. `i18n\build_qm.bat` (makes the `.qm` of every `.ts`; needs `lrelease` on the PATH; the `.qm` format is the same for Qt 5.3 and later),
4. rebuild.
